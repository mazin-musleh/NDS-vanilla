# NDS JS Audit — DRY/KISS + consistency rules (JSD)

DRY/KISS and cross-file-consistency detection catalog for `nds-js-audit`. Read during Phase 2/3 of a `dry` run (or any run with no rule-group filter). **JSD-05** (cross-file body dedup) needs the full tree — single-file `dry` skips it with the Phase 4 banner. **JSD-15** applies the canonicals in `PERSONA.md` (sibling file) per-file. Severity drives Phase 5 fix order. Audit flow: `SKILL.md`.

#### JS DRY/KISS (JSD)

| ID | What to detect | Severity | Fix |
|---|---|---|---|
| JSD-01 | Three sub-shapes. **(a) Direct `data-state` access** — `setAttribute('data-state', ...)`, `getAttribute('data-state')`, `removeAttribute('data-state')`, `hasAttribute('data-state')`, or assignment to `dataset.state`. The `hasAttribute` form bypasses `NDS.State` just like the others — existence reads still encode the same coupling.<br><br>**(b) `data-*-state` parallel state-machine attributes** — `setAttribute('data-<prefix>-state', ...)`, `getAttribute('data-<prefix>-state')`, `removeAttribute('data-<prefix>-state')`, `hasAttribute('data-<prefix>-state')`, or `dataset.<prefix>State` assignment, where the written/read values match a state-machine vocabulary: `open` / `closing` / `opening` / `closed` / `show` / `hide` / `shown` / `hidden` / `active` / `inactive` / `selected` / `expanded` / `collapsed`. A `data-<prefix>-state` attribute (e.g., `data-toast-state`, `data-menu-state`, `data-overlay-state`) is a parallel state machine that should consolidate onto `data-state` so a single `NDS.State` API serves the whole component — keeping multiple state attributes per element fragments the lifecycle and forces every reader to learn which attribute means what. Carve-out: `data-<prefix>` attributes whose values are NOT in the state-machine vocabulary (e.g., `data-position-vertical="top"`, `data-axis="x"`, `data-variant="primary"`) are configuration / positional / classification attributes, NOT state.<br><br>**(c) Attribute-selector queries against `data-state`** — `querySelector(...)`, `querySelectorAll(...)`, `matches(...)`, `closest(...)` whose selector string contains `[data-state~="<token>"]`, `[data-state="<token>"]`, `[data-state*="<token>"]`, or any other attribute-selector form targeting `data-state`, AND the embedded token matches the state-machine vocabulary listed under sub-shape (b) (`open` / `closing` / `opening` / `closed` / `show` / `hide` / `shown` / `hidden` / `active` / `inactive` / `selected` / `expanded` / `collapsed`). HTML-template writes that embed `data-state="<token>"` as a literal attribute inside an `innerHTML` string (e.g., `el.innerHTML = '<button data-state="active">'`) also count under (c) — the template bypasses `NDS.State.set` just like sub-shape (a)'s direct write. The selector form is the read-side analog of `hasAttribute('data-state')`: it queries by state token in a way that couples consumer code to the State vocabulary outside the State API, just as the `hasAttribute` form encodes existence-by-token outside the API. **Carve-out (vocab gate, sub-shape (c) only):** tokens NOT in the state-machine vocabulary list above — component-private classification tokens such as `today`, `other-month`, `sorted-asc`, `sorted-desc`, `range-start` — are NOT findings even when embedded in `[data-state~="<non-vocab-token>"]` selectors. JSD-01(c) is bounded to state-machine vocab by design; non-vocab tokens are component-private and the file owns both write and read, so the coupling is internal. Exemplar: `_js/nds-date-picker.js` `setActiveDayCell` (~L1967) documents the distinction inline (`'selected' / 'range-start' are state-vocab tokens → NDS.State.has; 'today' / 'other-month' are component-private → selectors stay as-is`). Carve-out: selectors targeting custom `data-*` attributes outside the state vocabulary (e.g., `[data-no-auto-close]`, `[data-dropmenu-no-click]`, `[data-position-vertical]`, `[data-filter]`) are configuration markers, not state — NOT a finding. Carve-out: when a component already maintains its own canonical state-tracking data structure (e.g., a module-level `Set` of open instances, like `_js/nds-mainnav.js:_openDropdowns`), the selector form is doubly wrong (it duplicates the source of truth); when no such structure exists yet, the fix may require adding one.<br><br>**Carve-out: foreign-written state-vocab reads (sub-shape (c) only).** When the queried `[data-state~="<token>"]` is written by something OTHER than this file — HTML template output (Liquid / Jekyll-rendered), or a sibling component that owns the token — the selector is the canonical entry-point: it reads state the file does not own, rather than duplicating state the file does. NOT a finding. **One detection test covers both sources:** grep the same file for `NDS.State.set` / `NDS.State.add` writes of that token; if zero writes of it exist anywhere in the file, the read is foreign and exempt. The recommended fix (iterate + `NDS.State.has`) would replace a single browser-optimized selector with a JS-level filter — strictly worse, no behavior change. Motivating examples (none a finding): `_js/nds-drawer.js` `initActiveStates` (~L257) reads server-rendered `li[data-state~="active"]` descendants to mark parent buttons; `_js/nds-sidemenu.js` `updateToggleLabel` (~L172) reads the server-rendered active item's label for the collapsed toggle; `_js/nds-dropmenu.js` `getCurrentItem` (~L624) reads `.nds-dropmenu-item[data-state~="active"]` where pagination and sort — not dropmenu — stamp the token, as its own comment says. Sibling-written is the same shape as server-rendered: the writer is elsewhere, so there is no in-file source of truth to prefer. | HIGH | Sub-shape (a): use `NDS.State.add/remove/has/get/set/clear/apply`. For `hasAttribute('data-state')` reads, use `NDS.State.get(el) !== ''` when testing for any state, or `NDS.State.has(el, 'specific-token')` when a specific token is known. Sub-shape (b): migrate the parallel state machine onto `data-state` using component-namespaced tokens (e.g., `data-toast-state="show"` → `NDS.State.add(toast, 'toast-show')` or `NDS.State.set(toast, 'shown')`). If the component genuinely needs two orthogonal state axes (rare — usually a redesign smell), use space-separated tokens on a single `data-state` rather than two attributes. Sub-shape (c): when iterating a known set, swap the selector for `NDS.State.has(el, token)`; when querying by state across an unknown scope, either track an instance/module `Set` (mirroring `_js/nds-mainnav.js:_openDropdowns`) or omit the attribute from any HTML template and call `NDS.State.set(el, token)` after `innerHTML` is set. If three or more files independently re-implement attribute-selector queries by state, surface as a JSD-05 promotion candidate for a core `NDS.State.queryByToken(scope, sel, token)` helper — the recurring pattern would justify a shared abstraction over per-component Sets. |

The `hasAttribute('data-status')` form bypasses `NDS.Status` just like the others. | HIGH | Use `NDS.Status.set/get/clear`. Status is a single value, not a set. | JSD-03 | Hardcoded layout pixels bypassing the token layer, in three sub-shapes: **(a) viewport comparisons** — any integer literal in `[400, 2000]` compared (`<`, `<=`, `>`, `>=`, `===`, `!==`) against `window.innerWidth`, `document.documentElement.clientWidth`, or `document.body.clientWidth`. The range captures the realistic viewport-breakpoint space while excluding unrelated small/large magic numbers (counts, sizes, timeouts). Off-by-one literals like `958` (near-desktop) or `1439` (near-large-desktop) are the main reason for widening beyond the canonical 768/1024/1280/1440 list; **(b) fallback literals** — the canonical breakpoint values (768/1024/1280/1440) used as the right-hand side of `\|\|` after `getComputedStyle().getPropertyValue(...)` parses a CSS variable (e.g., `parseInt(styles.getPropertyValue('--nds-...')) \|\| 1280`); **(c) `matchMedia` breakpoint literals** — any integer literal in `[400, 2000]` embedded inside a string argument to `window.matchMedia(...)` as part of a `min-width` / `max-width` / `min-height` / `max-height` media feature (e.g., `window.matchMedia('(max-width: 600px)').matches`, `window.matchMedia('(min-width: 601px) and (max-width: 960px)')`). Off-by-one literals like `601` / `961` are the common shape (media queries use inclusive edges while `NDS.breakpoints` picks one side as canonical), and they silently drift from the tokens on every re-audit. All three shapes hardcode the token into JS; (b) also hides a missing-CSS-var bug when the fallback silently takes over.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Numeric literals on the right-hand side of a module-scope `const` declaration whose identifier is SCREAMING_SNAKE_CASE (e.g., `CONTENT_MAX_WIDTH_FALLBACK`, `SLIDES_MAX_WIDTH`) AND which has a rationale comment within 3 lines above explaining why JS needs the numeric value. This IS the fix for sub-shape (b); re-flagging it on every audit run is noise. The detection fires on raw literals in comparisons or fallback positions, not on named-constant declarations that encode the token-layer shim.<br>- Integer comparisons against viewport width where the literal is OUTSIDE `[400, 2000]` — those are genuinely not breakpoint logic (thresholds for tiny embed widths, very-wide ultra-monitor layouts, etc.) and should be judged case-by-case rather than swept up by this rule.<br>- `matchMedia` strings embedded in feature-query syntax unrelated to viewport width/height (e.g., `(prefers-reduced-motion: reduce)`, `(hover: none)`, `(prefers-color-scheme: dark)`, `(pointer: coarse)`) — sub-shape (c) only catches literal integer pixel values inside `(min\|max)-(width\|height)` media features.<br>- `matchMedia` calls whose argument is `NDS.breakpoints.<token>` or a module-scope `const` with a rationale comment — the token layer is already in use, no finding. | MEDIUM | Viewport comparisons and `matchMedia` literals → use `window.matchMedia(NDS.breakpoints.mobile/tablet/'tablet-max'/desktop/'desktop-max'/'large-desktop').matches`. If the specific pixel threshold isn't in `NDS.breakpoints`, either add it to core or align the component to the closest existing token (e.g., `958` → `'desktop'` at 960px, `601` → `'tablet'` at 600px, `961` → `'desktop'` at 960px). Fallback literals → ensure the CSS variable is always defined in base styles so the fallback never fires, or extract the literal to a SCREAMING_SNAKE_CASE module-scope constant with a rationale comment explaining why JS needs the value. |
| JSD-04 | Re-implemented locale/direction check that duplicates `NDS.lang` / `NDS.isRTL` / `NDS.isArabic`. Two sub-shapes:<br><br>**(a) Direction/RTL checks:** `document.dir`, `document.documentElement.dir === 'rtl'`, `getAttribute('dir')` on `document.documentElement` or `document.body`, or equivalent reads of the `dir` attribute to derive RTL-ness.<br><br>**(b) Language checks:** `document.documentElement.lang`, `document.lang`, `document.documentElement.getAttribute('lang')`, or derivations that lowercase / prefix-split / compare-against-`'ar'` those values to produce a lang code (e.g., `(document.documentElement.lang \|\| 'en').split('-')[0].toLowerCase()`, `document.documentElement.lang.startsWith('ar')`).<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- `NDS.lang` / `NDS.isRTL` / `NDS.isArabic` definitions inside `nds-core.js` — that's the source of truth, not a duplicate.<br>- Per-element `lang` reads: `el.getAttribute('lang')` / `el.lang` where `el` is NOT `document.documentElement` / `document.body`. Component code may legitimately read per-element language overrides (e.g., a widget switching mid-page); that's not a duplication of the document-level `NDS.lang`.<br>- **Pre-loader standalone scripts.** A file that runs before `nds-loader.js` has no `NDS` to read — the document-level derivation IS the only option. Detection: the file's own `NDS.*` uses (if any) are existence-guarded (`window.NDS && NDS.<X>`), and it is not in the loader's `COMPONENTS` registry. Same reasoning as JSD-08's pre-loader carve-out. Motivating examples: `_js/nds-theme-hajj.js` and `_js/nds-theme-foundation-day.js` `LANG` (~L84 / ~L81) — event theme PACKs whose documented shape is a self-contained `<script src>` in `<head>`; their only `NDS` touch is a guarded `NDS.Swiper` call. Their local `esc` / `safeUrl` helpers are exempt from JSD-10 for the same reason.<br>- Per-element `direction` reads: `getComputedStyle(el).direction === 'rtl'` (or `=== 'ltr'`) where `el` is NOT `document.documentElement` / `document.body`. `NDS.isRTL` is a document-level signal and cannot answer per-instance direction questions — a component nested inside a `dir="…"` wrapper or styled via CSS `direction:` (e.g., chart canvases, embedded RTL widgets inside an LTR shell) must resolve direction at the element level. Motivating example: `_js/nds-chart.js:404` reads `getComputedStyle(this.el).direction` for per-chart RTL handling — a legitimate use case that `NDS.isRTL` cannot satisfy. | MEDIUM | Use `NDS.isRTL` (live getter) or `NDS.lang` / `NDS.isArabic`. |
| JSD-05 | **Promotion candidate.** Two sub-shapes, both requiring no equivalent in `nds-core.js`.<br><br>**(a) Named-helper duplication** — a helper function with near-identical signature and body appears in two or more component files.<br><br>**(b) Canonical-idiom inline expression** — a canonical idiom **with a body worth sharing** appears as a bare inline expression in **three or more** component files, whether or not any file wraps it in a named helper. Sub-shape (a) misses these: an idiom nobody bothered to name never trips a name-based scan even when the site count is higher than (a)'s bar. The higher threshold (3 files, vs (a)'s 2) keeps a two-site coincidence from minting an API. **Body gate — the idiom must be multi-statement or carry a branch.** A single expression with no branches cannot diverge between copies, so a shared implementation prevents no bug-fix drift; promoting one buys a project-local name for something the reader already parses fluently, and pays for it in core bytes on the reveal-gating main bundle plus a permanent published-API commitment (removal later needs a CHANGELOG Migration entry). In scope from JSD-10's idiom list: HTML escape (chained `String.replace`, or the `createElement` → text-safe assign → read `innerHTML` round-trip), debounce/throttle (stored timer/flag + inner call). Out of scope: **clamp** — `Math.min(Math.max(v, lo), hi)` is one expression, and JS ships no `Math.clamp`, so the composition IS the idiom; `_js/nds-ipv.js` `clamp` (~L123) plus the inline sites in `_js/nds-filter.js` (~L1889-1890) and `_js/nds-pagination.js` (~L738, ~L1565) clear the 3-file count and still correctly produce no finding. Detection: for each in-scope idiom, grep its shape tree-wide and count DISTINCT files; a file contributes once regardless of how many sites it holds.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Sub-shape (b) matches where the idiom's operands make the sites semantically unrelated — the shape is shared but no single signature serves every caller. Record as a Gap.<br>- Idioms the language ships natively (route to the ponytail `PONY-STD` lens instead of minting an `NDS.*` name): JS has no `Math.clamp`, so clamp stays in scope here, but a hand-rolled `Array.from` / `flat` / `structuredClone` equivalent does not. | MEDIUM | Propose an `NDS.*` API name and list every call site. Typical candidates: focus-trap, scroll-lock, `getComputedStyle` readers, `matches()` / `closest()` helpers, RAF batchers, event-delegation factories, z-index stackers, `aria-expanded` toggles. Surface the candidate in the Phase 4 report; editing `nds-core.js` to add the helper + migrating every call site is a Phase 5 action the user approves per-candidate via `promote <api-name>` (see "Applying promotion candidates" in `FIX.md`). |
| JSD-06 | DOM read after write in the same frame (e.g., `setProperty` then `getBoundingClientRect` in a loop).<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Standalone forced-reflow triggers (`void el.offsetHeight;` or `el.offsetHeight;` as the sole statement on its line) are deliberate transition-start patterns, not thrashing.<br>- Staged-measurement patterns: a write to `style.cssText` / `style.visibility` / `style.position` that puts an element into a measurable off-screen state, followed by `offsetHeight` / `offsetWidth` / `getBoundingClientRect()` reads. The read semantically depends on the write (the element must be staged before it can be measured), so "batch reads before writes" does not apply. Require an inline comment near the write confirming the staging intent to earn this exemption — otherwise it's indistinguishable from a thrash loop.<br><br>Thrashing is a LOOP pattern (N writes × N reads within one synchronous block). One-shot write-then-read sequences are not thrashing. | LOW | Batch reads before writes: collect every layout read into locals first, then apply all writes. Exemplar: `_js/nds-core.js` `NDS.flipPosition` (~L1216) — collects `triggerRect` / viewport dims into locals before any positional write. |
| JSD-07 | **Component contract conformance.** A `_js/nds-{name}.js` file whose public surface does not match one of the two shapes the loader expects. Factory components must expose `NDS.{Name}.init()`, `NDS.{Name}.reinit()`, and `NDS.{Name}.create(el)`. Singletons must expose `NDS.{Name}.init()` plus their component-specific methods. The namespace `{Name}` must match the component's `_js/nds-loader.js` `COMPONENTS` registry name — compound single-word suffixes camel-case per that registry (`nds-customselect.js` → `NDS.CustomSelect`, `nds-taginput.js` → `NDS.TagInput`); do not flag against a mechanical PascalCase of the suffix ("Customselect", "Taginput").<br><br>**Explicitly NOT a finding** (transient-surface exemption): a module whose `create()` takes an OPTIONS OBJECT and builds a new surface — PERSONA entry 3.3's `create({…})` + `dismiss(target)` bucket — rather than taking an element and instancing it. Its `create` is the constructor entry for a surface with a finite lifetime, not a per-element factory, so the factory triple does not apply and a missing `reinit()` is correct, not drift. Such a module may ALSO run a one-time document sweep in `init()` (wiring close buttons on server-rendered instances) without becoming a factory — the sweep builds no instance and registers no expando. (Citation expired — `_js/nds-voice-recognition.js` was merged into `_js/nds-voice-input.js`; no standalone utility module currently exists in the tree. The exemption stands for the next one.) | MEDIUM | Restructure the module to match the shape of the closest peer (factory example: `_js/nds-modal.js`; singleton example: `_js/nds-theme.js`). Inconsistent shapes force every reader to relearn the API per component and block the loader from treating components uniformly. For utility modules covered by the exemption above, no fix is required — but a one-line comment near the namespace export naming the consuming components keeps future audits from re-flagging. |
| JSD-08 | **Dead defensive guards.** Inside a component registered with `nds-loader.js`, checks like `typeof NDS !== 'undefined'`, `typeof NDS.X !== 'undefined'`, `NDS && NDS.X`, the `window.`-prefixed variants (`window.NDS && window.NDS.X`, `window.NDS && NDS.X`, any mix), OR the optional-chaining variants (`NDS?.X?.method()`, `NDS.X?.method()`, `NDS.X?.subProp`) used as preconditions before calling core APIs. Detection covers bare-`NDS`, `window.NDS`, AND optional-chaining (`?.`) forms. The loader guarantees `NDS` and every registered namespace exist before any component's `init()` runs, so these guards are dead code that implies uncertainty the loader contract explicitly denies. Multi-part guards where ONLY the final method-existence check is load-bearing (e.g., `NDS && NDS.Forms && NDS.Forms.validateForm`) collapse to just the final call when the API is unconditionally assigned — verify by grepping `NDS.{Namespace} = {` in the owner module to see if the method lives inside an always-present object literal.<br><br>**Explicitly NOT a finding** (do NOT flag these as JSD-08):<br>- `typeof window !== 'undefined'` / `typeof document !== 'undefined'` — runtime-environment guards protecting against SSR/Node execution, not loader-contract guards. | JSD-09 | **Teardown references properties never stored, or stored handles never invoked.** Four sub-shapes:<br><br>**(a) `this.handlers.{name}` map shape** — Inside any teardown path (function named `cleanup` / `destroy` / `teardown`, or any function containing `removeEventListener(..., this.handlers[name])` — either in a loop over named keys OR as straight-line `removeEventListener` calls referencing `this.handlers.{name}` directly), every handler key referenced must have a matching assignment `this.handlers.{name} = ...` somewhere else in the same file. A teardown that dereferences `this.handlers.foo` when `foo` was never stored is dead-code-pretending-to-clean-up: the `removeEventListener` call receives `undefined` and silently does nothing. Detection: for each `this.handlers.{name}` or `this.handlers[name]` reference inside a teardown path, grep the file for `this.handlers.{name} =` or `this.handlers[{name-literal}] =`.<br><br>**(b) Instance-property handler shape** — `removeEventListener(..., <owner>._handlerName)` or `removeEventListener(..., <owner>.<propName>)` (where `<owner>` is `this`, an instance reference, or a closure-scoped variable; `_handlerName` / `propName` is a single identifier, not a method call). Same detection as (a) but generalized: grep the file for `<owner>._handlerName =` / `<owner>.<propName> =`. If no assignment exists, the call receives `undefined` and silently noops. JSD-05 is the most qualitative rule: require ≥2 distinct files with substantially-overlapping bodies (sub-shape (a)) or ≥3 distinct files carrying the same canonical idiom (sub-shape (b)) before flagging, and name the proposed API naturally (`NDS.trapFocus(el)`, not `NDS.helperFn7`).

JSD-14 has the highest false-positive risk in JSD. Skip the finding if a sub-shape match has a defensible rationale in context (e.g., deep nesting that mirrors a state machine the reader needs to see linearly; a redundant guard that documents an invariant the next reader would otherwise miss). When in doubt, record as a Gap observation rather than a finding — the rule earns its keep by sharpening over time, not by padding the report.

JSD-15's false-positive defense is `PERSONA.md` itself. The persona's per-entry carve-outs name the concept-different cases that look like divergence but aren't (transient toasts using `show`/`hide` vs modals using `open`/`close`; the date-picker two-phase `cleanup()`+`destroy()` vs single-method instances; `window.nds<Name>Initialized` flags for tree-wide observers in tables.js). The audit MUST read these carve-outs before flagging — a file matching a documented carve-out's discriminator is NOT a finding. When divergence is real but the canonical itself feels wrong for the case at hand, the answer is a Phase 7 EVOLVE proposal to revise the canonical with the file's reasoning, not a quiet skip — the persona changes through deliberate revision, never through silent erosion.
