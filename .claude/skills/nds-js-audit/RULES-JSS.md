# NDS JS Audit — Security rules (JSS)

Client-side web-security sink catalog for `nds-js-audit`. Read during Phase 2/3 of a `security` run (or any run with no rule-group filter). Severity is calibrated to exploitability in a Jekyll static-site context. Audit flow: `SKILL.md`. Other groups: `RULES-JSP.md` / `RULES-JSD.md` / `RULES-JSA.md`.

#### JS Security (JSS)

Web-security sinks that commonly appear in vanilla-JS component code. Severity is calibrated to exploitability in a Jekyll static-site context: a reflected XSS through an NDS component is HIGH because the component ships everywhere; a same-origin `window.open` with a developer-controlled `data-*` attribute is MEDIUM. Each JSS finding must name the untrusted-input source in plain language — "this `${title}` comes from `NDS.Alert.create()` options, which callers can fill with arbitrary strings" — so the fix cost is visible alongside the risk.

| ID | What to detect | Severity | Fix |
|---|---|---|---|
| JSS-01 | **HTML sink fed an unescaped substitution.** `el.innerHTML = X`, `el.outerHTML = X`, `el.insertAdjacentHTML(pos, X)`, `document.write(X)` / `writeln(X)`, or the same call on any `Document` reference (`iframe.contentDocument`, `popup.document`, `globalThis.document`), where `X` is a template literal or `+` concatenation with a non-literal substitution: classic XSS. Focus on sinks that interpolate caller-supplied values (component options, `dataset` reads, API responses, `getAttribute`). `check-js-rules.mjs` finds the sinks and lists every substitution it cannot prove safe: it passes a helper named `*escape*`, a number or boolean, a loop counter, a fixed string, a module-scope literal constant, a ternary of fixed strings, or a variable assigned only from those. The `<documentRef>.write` shape is the iframe-init idiom (build a full `<!doctype html>` document, hand it to `iframe.contentDocument.write`) where DOM construction via `createElement` is impractical; the same escape rules apply. Reference shape for doc-write: `_js/nds-export.js` `openPrint` (~L354) builds a print iframe via `doc.write(html)`; text goes through `NDS.escapeHtml`, and the theme colours inside its `<style>` pass `CSS.supports('color', x)` in `readTableTokens` (CSS context needs a value check, not an HTML escape).<br><br>**Explicitly NOT a finding** (the script hands these to you, or does not encode them):<br>- Instance/object property read `<obj>.<prop>` (or chained `<obj>.<prop1>.<prop2>`) where EVERY assignment to `<prop>` anywhere in the same file resolves to a value the script treats as safe (a number, boolean, loop counter, `.length`, `parseInt` / `Number` / `Math.*` result, or arithmetic of those). Whole-file scope. Covers by-construction numeric fields (`this.totalSteps`, `this.currentStep`, `this.activeIndex`). A single assignment outside those anywhere in the file disqualifies the property entirely — partial coverage doesn't count. Disqualifying chains: `this.opts.colors[i]`, `getAttribute` / `dataset` / `localStorage` reads, non-allowlisted function-call returns.<br>- Interpolations wrapped in the file's own escape helper (`${encodeEntities(x)}` or equivalent defined in the same file); the script recognises only helper names containing `escape`.<br>- Annotation exemption (global) naming the specific source of the value AND why it is safe (e.g., `// XSS-safe: icon class comes from TYPE_DEFAULTS keys, not user input`).<br>- Sinks on freshly-created elements where the value was already `.textContent`-assigned elsewhere (handled as a combined read).<br><br>**Critical override — taint-source escalation.** None of the exemptions above apply when the value's nearest assignment chain reads from a same-origin-writable store: `localStorage.getItem(...)` / `sessionStorage.getItem(...)` / `document.cookie` / a same-file helper wrapping any of these. Same-origin XSS in another page, malicious extensions with `storage` access, or dev-tools paste can plant attacker-controlled HTML; the next render injects it. The taint-source escalation is a HIGH finding regardless of which exemption otherwise applied. Trace the RHS variable's most recent assignment, through any same-file helper, to a writable-store read; the script labels only a direct read. Fix is `NDS.escapeHtml(cached)`, OR migrate the producer to write `.textContent`-safe data only, OR an annotation naming the store AND why the cached payload is trusted (e.g., "// XSS-safe: cache writer at L88 escapes via NDS.escapeHtml before storing"). | HIGH | **Primary**: wrap every caller-supplied substitution in `${NDS.escapeHtml(x)}` — escapes `& < > " '`, so it is safe in text and in QUOTED attribute values. One-line per substitution. Unquoted attributes, URLs (`NDS.safeUrl`) and `style`/script contents still need `setAttribute` / the CSSOM rather than interpolation. **Secondary** (mixed-chrome templates / avoid innerHTML entirely): build DOM via `document.createElement` and assign dynamic values through `.textContent` / `.setAttribute`. **Never hand-roll a local escape** — route through `NDS.escapeHtml`. |
| JSS-02 | `check-js-rules.mjs` finds the literal forms; a string-valued variable handed to a timer is the deep read's. Dynamic code execution sinks: `eval(x)`, `new Function(...args, body)`, `setTimeout(x, ...)` / `setInterval(x, ...)` where the first argument is a string literal or a string-valued variable (not a function reference, arrow, or function expression). The browser will parse and execute the argument as JavaScript, bypassing every escape upstream and skating past any CSP `script-src` restriction that doesn't include `'unsafe-eval'`. There is no legitimate use case for any of these in NDS component code. | HIGH | Replace with a direct function call. `setTimeout('foo()', 100)` → `setTimeout(foo, 100)`. For dynamic dispatch (action name → handler), use a lookup object: `({ next: goNext, prev: goPrev }[action] ?? noop)()`. If you genuinely need to parse user-supplied expressions (extremely rare for UI code), sandbox it in a Worker with a dedicated parser — not in the main realm via `eval`. |
| JSS-03 | **RETIRED — never flag, never "fix".** Formerly: an `<a target="_blank">` with no `rel="noopener"`. Every browser NDS supports has implied `noopener` for `target="_blank"` since 2021, so reverse-tabnabbing is unreachable and the attribute buys nothing. NDS deliberately does **not** force `rel` on external links — `NDS.Link` tags `target="_blank"` only, so the destination site keeps its referrer. Do not report a missing `rel`, and do not add one. A link that genuinely needs `noreferrer` (untrusted or pasted `href` in editor content) is an explicit author call and is already set at those sites. | — | — |
| JSS-04 | (`check-js-rules.mjs` finds it; a same-realm `MessageChannel` port is `verify`.) `addEventListener('message', handler)` on `window`, `self`, or any EventTarget where the handler body does NOT read `event.origin` (destructured `origin` also counts) and compare it against an expected value before touching `event.data`. Any frame on the page — including an attacker-controlled one in an iframe or a tab that holds a window reference — can send a forged `postMessage` with data that drives the handler's actions.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- `onmessage` / `addEventListener('message', …)` handlers on a `MessageChannel` **port** (`new MessageChannel().port1` / `.port2`) created in the SAME realm, where neither port is transferred to another realm/document — i.e. NOT a `MessagePort` received via a `window` / `self` `'message'` event's `event.ports`, and neither port is handed to a worker / iframe / `window.postMessage`. A same-realm `MessageChannel` is a closed two-party channel (no external frame can reach it) and `MessagePort` message events carry no security-meaningful `origin` (it's always the empty string), so an origin check is impossible and pointless. Reference safe shape: `_js/nds-loader.js` `yieldToBrowser` (~L396) (`yieldChannel` — `port2` is closure-private, used only for `postMessage(null)` as a yield signal; the handler ignores `event.data`).<br>**Still a finding** (do NOT exempt): a `MessagePort` obtained from `event.ports` of a `window` / `self` `'message'` event (that port came from an untrusted sender — validate the originating message's `event.origin` first); any `BroadcastChannel` `onmessage`; a worker / iframe `onmessage` reachable cross-context; or any `MessageChannel` where EITHER port is exposed cross-realm (transferred via `postMessage` or a public NDS API) — once a port leaves the realm the channel is no longer closed, so the handler on the other port is attacker-reachable. | HIGH | Validate origin as the first check in the handler. For a fixed-origin setup: `if (event.origin !== 'https://trusted.example') return;`. For an allowlist: keep a `Set` of allowed origins and early-return on miss. Never compare against `'*'` (no-op), never rely on `event.source` alone (it proves the sender, not the origin), and never skip the check for same-origin-only deployments — same-site subdomains and intermediary frames still cross the origin boundary. |
| JSS-05 | **Navigation sink fed an expression.** `window.open(x, ...)`, `window.location = x`, `location.href = x`, `location.assign(x)` / `location.replace(x)`, `a.href = x`, `a.setAttribute('href', x)` (the last two when `a` is a newly-created anchor), where `x` is a variable, template literal or expression that can come from `getAttribute('data-*')`, `dataset.*`, URL query parameters, form-input values, server-response fields, `postMessage` data, or caller-supplied component-options fields (e.g., an `actions: [{ href }]` entry passed to a `create()` API). Without scheme validation, a `data-share-url="javascript:alert(1)"` attribute becomes script execution when the user clicks.<br><br>The rule has two independent concerns, and an exemption from one does NOT exempt the other: (1) **noopener** — does the new context retain a back-reference to the opener? (2) **scheme** — does the URL parser execute a `javascript:` / `data:` / `vbscript:` payload? `check-js-rules.mjs` decides the noopener dimension (`window.open` with no feature string keeps the opener; a non-empty feature string makes modern browsers default to noopener) and lists every non-literal destination for the scheme dimension.<br><br>**Explicitly NOT a finding for the scheme dimension** (the script hands these to you):<br>- Values already passed through `encodeURIComponent` for use as query-string parameters (the scheme is whatever the base URL sets, not what the encoded component is).<br>- Values that flow through a same-file scheme-validation helper (`new URL(x, location.href)` checked against an `http:`/`https:`/`mailto:`/`tel:` allowlist) before the navigation sink.<br>- A value that comes from no attribute, option or response (trace its source).<br><br>**Critical**: when `x` traces back to `dataset.*` / `getAttribute('data-*')` / `postMessage.data` / form-input / server-response, the scheme dimension fires regardless of whether the noopener dimension is satisfied by a feature string. | MEDIUM | Validate the URL's scheme before navigating. Compact form: `try { const u = new URL(x, location.href); if (!['http:', 'https:', 'mailto:', 'tel:'].includes(u.protocol)) return; window.open(u.href, '_blank', 'noopener'); } catch { return; }`. For internal navigation, assert the value begins with `/` or `#` before assigning. For share/copy flows (see `_js/nds-share.js` `getShareUrl` (~L50)), apply the scheme check inside the URL-reading helper so every caller benefits. |
| JSS-06 | **Prototype pollution via JSON-from-writable-store fed into `Object.assign` / object-spread.** `JSON.parse('{"__proto__":{"polluted":1}}')` produces an own data property named `__proto__`; `Object.assign` and spread call `[[Set]]` for each source own key, which for `__proto__` replaces the target's `[[Prototype]]` with the attacker-controlled object. Same-origin XSS on any other page of the origin, a malicious extension with `storage` access, or a dev-tools paste can plant the payload; the next page's rehydration takes the assignment. The damage stays bounded to the rehydrated object while it is read only by known keys (`state.modes`), but leaks into legitimate logic once it is iterated, spread into another assign, or used as a key map (`if (key in state)`). `check-js-rules.mjs` finds a value parsed from `localStorage` / `sessionStorage` / a cookie (directly or through a same-file helper) used as an `Object.assign` source or spread, unless `NDS.i18n.safeMerge`, a `delete …__proto__` or an `Object.create(null)` target is in view.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Sources that pass through an own-key filter the script does not recognise — an explicit `for (const k of Object.keys(parsed)) { if (k === '__proto__' \|\| k === 'constructor' \|\| k === 'prototype') continue; ... }` loop, or a `delete parsed.constructor;` chain immediately preceding the assign.<br>- Annotation exemption (global) naming the writable store AND why the rehydrated payload is trusted (e.g., `// safe: cache writer at L88 only stores values from TYPED_VALUES`). | MEDIUM | Route the parsed source through `NDS.i18n.safeMerge(target, parsed)`. The helper `NDS.i18n.safeMerge` at `_js/nds-core.js` (~L298) copies own enumerable keys via `Object.keys` and skips `__proto__` / `constructor` / `prototype` — equivalent to `Object.assign` for legitimate keys, hardened against the prototype-key vector. For the multi-source Object.assign shape, replace each writable-store source individually: `Object.assign(target, literal, NDS.i18n.safeMerge({}, parsed), other)` — pass through a fresh own-keys copy. If the consuming object should never have a non-default prototype, switch the target to `Object.create(null)` for full immunity (works whether or not any source is filtered). The helper currently lives under `NDS.i18n` for historical reasons; if non-i18n callers proliferate, surface a JSD-05 promotion candidate to lift it to top-level `NDS.safeMerge`. |

JSS-01 is the highest-false-positive rule in the catalog — static-analysis can't prove that a component-options value is safe at the caller level. When the codebase legitimately trusts a value (e.g., icon class names resolved from a `TYPE_DEFAULTS` enum in the same file), prefer the annotation-exemption comment over widening the rule's numeric/helper allowlist. If the same "safe by construction" rationale repeats across three or more sites, that is a JSD-05 promotion candidate (the rationale becomes a typed enum or helper).
