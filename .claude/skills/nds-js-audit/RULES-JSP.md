# NDS JS Audit — Performance rules (JSP)

Performance detection catalog for `nds-js-audit`. Read during Phase 2/3 of a `performance` run (or any run with no rule-group filter). Severity (HIGH/MEDIUM/LOW) drives Phase 5 fix order. Audit flow: `SKILL.md`. Other groups: `RULES-JSD.md` / `RULES-JSS.md` / `RULES-JSA.md`. JSD-15 persona canonicals: `PERSONA.md`.

#### JS Performance (JSP)

| ID | What to detect | Severity | Fix |
|---|---|---|---|
| JSP-01 | `addEventListener(['"']resize['"']` on `window` (`check-js-rules.mjs` finds it) | HIGH | Replace with `NDS.onResize(handler)` — it already debounces at 150ms and pools subscribers. |
| JSP-02 | A `scroll` listener whose handler has no rate limit (`check-js-rules.mjs` finds it). The script traces the handler (inline, a same-file function, or a name bound to a wrapper) and passes: `requestAnimationFrame(`, `NDS.rafThrottle(`, `NDS.debounce(`, `NDS.onResize(`; a call to a function bound to `NDS.rafThrottle` / `NDS.debounce`; a custom wrapper whose body uses `requestAnimationFrame`; a handler that removes its own listener, directly or one call deep (a single-shot dismiss, where a throttle only delays the close); and a body of one attribute guard plus one write (`_js/nds-swiper.js` `data-swiper-moving`). A handler it cannot find in the file is `verify`. Still a finding: a bare `setTimeout` debounce (JSP-07's), a wrapper throttled with `setTimeout`, a scroll-position threshold, `requestIdleCallback`, `passive: true`. | HIGH | Wrap in RAF throttle using `NDS.rafThrottle(fn)`. Copy the pattern from the `checkScrollPosition` scroll listener in `_js/nds-scroll-more.js` (~L190). |
| JSP-03 | `new IntersectionObserver` (`check-js-rules.mjs` finds it). **Not exempt**: singleton usage, single-element observation, proper `disconnect()`/`unobserve()` disposal, or manual pooling do NOT make this compliant. The rule is about routing through the shared `NDS.onIntersect` pool so observers are grouped by threshold/rootMargin across the whole app — not about leak prevention. A well-disposed bare `new IntersectionObserver` is still a finding. | MEDIUM | Replace with `NDS.onIntersect(el, handler, { threshold, rootMargin })`. Core pools observers by threshold/rootMargin automatically. Store the returned unsubscribe handle. |
| JSP-04 | `check-js-rules.mjs` decides (a) and (b); (c) needs a read.<br><br>**(a) Raw `new ResizeObserver`.** Always a finding: the shared `NDS.onElementResize` pool replaces it, whether singleton, single-element or locally disconnected.<br>**(b) A pool call whose unsubscribe handle is dropped** (`NDS.onResize`, `onElementResize`, `onIntersect`, `onOutsideScroll`, `onAttrChange`, `onDOMAdd`, `onDOMRemove`, `onChildrenChange` as a statement of its own). In per-instance or re-callable code the callback leaks for the page lifetime and re-init stacks fresh ones; the dedup pools do not catch a fresh closure. The script passes the module IIFE body, a `document` / `document.body` / `document.documentElement` host, an `onDOMAdd` with a matching `onDOMRemove`, a dedup pool (`onElementResize` / `onIntersect`) handed a stable function reference, and a one-shot latch (`if (done) return; done = …` or `if (!done) { done = true; … }`). Its `verify` lines leave a once-per-page bootstrap or an annotation naming why the closure is acceptable.<br>**(c) Destroy bypasses the lifecycle method that releases stored `NDS.on*` handles.** When a component stores pooled-subscription handles inside an `open()` / `show()` / `enter()` lifecycle method (e.g., `this._offScroll = NDS.onOutsideScroll(scope, …)`, `this._unsubResize = NDS.onResize(…)`) AND releases them inside the matching `close()` / `hide()` / `exit()` method, but the component's `destroy()` / teardown path does NOT first call that lifecycle method when the component is in the open state, destroying an already-open component leaves the pooled subscription wired forever. The portal/state side effects (e.g., a menu still in the top layer) compound the leak: the closure is rooted by the pool, the moved DOM is rooted by the closure. Sub-shape (b) doesn't fire (the handles ARE stored), and sub-shape (a) doesn't apply (no raw observer). Detection: identify a `destroy()` / `teardown()` / `dispose()` method that does NOT reference the close-lifecycle method by name, AND verify the open-state handle assignments live inside `open()` / `show()` rather than the constructor. Severity stays MEDIUM because the leak only fires on the rarer "destroy while open" path — but each occurrence permanently strands a pooled subscription.<br><br>**Raw-listener variant.** The same hazard applies when a component pairs `bindXxx()` / `unbindXxx()` methods around raw `window.addEventListener` / `document.addEventListener` calls (typically rate-limited via `NDS.rafThrottle` to satisfy the JSP-01 / JSP-02 live-positioning carve-outs), invoked from `open()` / `close()` respectively. If `destroy()` does not reference `unbindXxx()` (directly or via the close path), the raw listener leaks for the page lifetime when destroy fires while open. Detection: a `bindXxx()` / `unbindXxx()` pair attaching window/document listeners, AND `destroy()` does NOT call `unbindXxx()` or the close-lifecycle method.<br><br>**Explicitly NOT a finding** (sub-shape (c) only):<br>- Constructor-attached subscriptions released in `destroy()` directly (already covered by sub-shape (b)'s positive case).<br>- `destroy()` calls the close-lifecycle method (`if (this.isOpen) this.close();`) before teardown work — release path runs through the existing close handler.<br>- `destroy()` aborts an `AbortController` that scopes the open-state subscriptions (rare with pooled subs since `NDS.on*` doesn't accept `signal`). | MEDIUM | Sub-shape (a): replace with `NDS.onElementResize(el, handler)`. Returns an unsubscribe function; store it for teardown. Sub-shape (b): capture the returned handle on the instance / closure / module scope (e.g., `this._offResize = NDS.onElementResize(el, handler);` or `let _off; ... if (_off) _off(); _off = NDS.onAttrChange(...);`) and invoke it in `destroy()` / `cleanup()` / re-init. For module-level singletons whose `init()` may run more than once, either guard the registration behind a `let _wired = false;` flag, or capture the handle and release the prior one before re-registering. Sub-shape (c): make `destroy()` drive the close-lifecycle method when the component is open — `if (this.isOpen) this.close();` as the first statement of `destroy()`. The close path already releases the handles and reverses any portal/state side effects, so destroy stays a thin wrapper. Alternatively, lift the open-state subscriptions to instance-lifetime (constructor) and gate them with an `if (!this.isOpen) return;` inside the handler — but that pays the always-on subscription cost for the rare-open case, so the lifecycle-driven path is preferred. Raw-listener variant: same fix — `destroy()` prepends `if (this.isOpen) this.close();` or calls the matching `unbindXxx()` directly before any teardown work. |
| JSP-05 | `new MutationObserver` (`check-js-rules.mjs` finds it; a comment above it makes the line `verify`, for the annotation below).<br><br>**Not exempt**: observing a single element, attaching once at setup, or `observer.disconnect()` on teardown do NOT make this compliant. One MutationObserver per component scales linearly with component count; the NDS pool keeps one observer per configuration and dispatches by selector.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Annotation exemption (global): the comment must name which pool limitation forces the local observer — e.g., content-mutation semantics (`characterData`, text-node observation), cross-frame observation, or other mutation types outside the pool's API. An escape hatch for cases the pool genuinely doesn't cover, not an opt-out for "I didn't bother". | MEDIUM | Replace with `NDS.onDOMAdd(selector, handler)`, `NDS.onDOMRemove(selector, handler)`, or `NDS.onAttrChange(selector, attrs, handler)` depending on mutation type. |
| JSP-06 | `addEventListener` without a matching `removeEventListener` or a stored unsubscribe returned by `NDS.on*`. A listener nothing releases stacks on every re-init and leaks when a consumer removes and recreates the component. `check-js-rules.mjs` lists sub-shape (a) as `verify` (per-element listeners attached in a loop with no `signal`; a per-element guard may let them self-clean) and finds (c) (a single `document` / `window` listener added in a constructor, instance `init()` or `setup*()` with no `signal` and no stored reference for a later `removeEventListener`; it scales O(n) with component count and leaks per reinit), one finding per loop, so count the listeners in it. It treats any `{ signal }` as released: a per-instance `this._ac` signal must still be aborted in `destroy()`, which you check.<br><br>**(b) Dynamic re-attach pattern**: a function attaches per-element listeners, is called more than once per lifecycle (event handlers, re-init paths, data/dir/lang re-renders), AND does NOT detach prior listeners before re-attaching. Two sub-shapes:<br>  **(b.1) forEach/for-loop shape** — attachments live inside a `forEach`/`map`/`for` loop.<br>  **(b.2) Sequential addEventListener shape** — sequential `addEventListener` calls on freshly-rebuilt nodes (typically inside `render()`/`redraw()`/`rebuild()` that does `el.innerHTML = ''` then re-creates children). Listeners attached via `this._ac.signal` where the controller is aborted ONLY at `destroy()` are STILL a finding: the `AbortSignal` retains references across re-renders until destroy fires, so the abort-handler chain grows linearly. Detection: a method that (i) is called more than once per lifetime, (ii) attaches per-element listeners (with or without `this._ac.signal`), AND (iii) does NOT reset the controller (`this._ac.abort(); this._ac = new AbortController()`) before re-attaching.<br>In both sub-shapes, listeners stack per invocation.<br><br>**Explicitly NOT a finding** (sub-shape (b.2) only):<br>- Methods that reset their controller before re-attaching (e.g., `if (this._renderAC) this._renderAC.abort(); this._renderAC = new AbortController();` at the top).<br>- Per-render controllers stored on the rebuilt element (`overlay._ac = new AbortController()`) where the prior overlay's controller is aborted before `innerHTML = ''`.<br>- Single-render components — methods called exactly once per lifetime. If not re-callable, no stacking.<br><br>**Explicitly NOT a finding**:<br>- forEach/for loops whose prior matching nodes are removed before re-creation — the parent cleared via `innerHTML = ''` / `replaceChildren()`, or the nodes themselves removed via `.remove()` / `removeChild()` earlier in the same chain — removed DOM takes its listeners with it. Exemplar: `renderChips()` in `_js/nds-taginput.js` / `_js/nds-multiselect.js` (per-chip `.remove()` sweep, fresh nodes re-attached per render).<br><br>**Sub-shape (a) factory variant** — missing `destroy()` path: factory components with forEach/for listener loops in constructor/init, NO `this._ac`, NO public `destroy()` method. The init guard (e.g., `data-nds-foo-initialized`) prevents stacking per page load, but consumers who remove and recreate the component cannot clean up. Both conditions required: (1) listeners in a loop with no AbortController signal, (2) no `destroy()` anywhere in the file.<br><br>**Explicitly NOT a finding** (factory-variant only): listeners bound DIRECTLY to content elements (`el.addEventListener(...)` where `el` is the swept element itself, not a stable parent or an outliving closure target) AND each element carries a per-element one-shot init guard (`el._ndsXxxInitialized` JS property or `data-nds-<name>-initialized` attribute set on first visit). Such listeners are reclaimed by GC when the element leaves the DOM, and the per-element guard prevents re-attachment on re-sweep — so there is no stacking and no leak, even without a `destroy()`. The factory-variant targets the case where teardown is genuinely impossible (listeners rooted by a surviving closure, or re-attached without a guard); element-bound + guarded listeners self-clean. Exemplar: `_js/nds-form.js` binds element-scoped listeners on specialized form controls (select, switch, number-input, clear-button, validation groups), each guarded by a per-element marker (`switchTrack._switchInitialized`, `btn._ndsNumberInit`, `group._checkGroupInitialized`, etc.) — element-scoped, GC-reclaimed on removal, not a finding. (Generic input chrome — active/focus/typing/sanitize/validate — is wired ONCE via document-level delegation in `installFormDelegation`, not per element, so it isn't a per-element-listener case at all.) | MEDIUM | Sub-shapes (a) and (b): store the unsubscribe handle (`wrapper._offResize = NDS.onResize(...)`), or attach an `AbortController.signal` to every listener so `.abort()` cleans atomically. For dynamic re-attach, abort the previous controller before creating a new one, or use delegated listeners on a stable parent. Sub-shape (c): add `this.abortController = new AbortController()` to the constructor (PERSONA entry 1 naming — never `this._ac`), pass `{ signal: this.abortController.signal }` to the listener, abort in `destroy()`. See `_js/nds-tabs.js` (`this.abortController` constructor assignment ~L74, signal-wired ~L144, destroy teardown ~L335). |
| JSP-07 | **Trailing-edge debounce only.** A hand-rolled `clearTimeout(t); t = setTimeout(() => fn(...args), CONST_MS)` wrapper called per event is exactly what `NDS.debounce(fn, ms)` wraps, so the `clearTimeout` bookkeeping belongs in the helper. `check-js-rules.mjs` lists the candidates (a constant literal ms, no second `clearTimeout` on the same variable); confirm each runs per event, not as orchestration.<br><br>**Explicitly NOT a finding** (do NOT flag — these match the surface pattern but the recommended fix doesn't apply):<br>- **Single-pending-action latches.** `clearTimeout` + `setTimeout` calls used as a manual one-shot scheduler — caller invokes `schedule()` and `cancel()` explicitly to orchestrate animations / timing-dependent state, not to throttle event-handler invocations. NDS.debounce returns a wrapper that callers invoke per event; replacing the latch's internal `setTimeout` with `NDS.debounce` would change call-site semantics. Recognized by: one explicit `cancelXxx()` / clear function paired with a `scheduleXxx()` / set function, with at least one caller invoking `cancelXxx()` separately from `scheduleXxx()`. Motivating example: the `scheduleToggleAction` / `cancelToggleAction` pair in `_js/nds-main-nav.js` (~L165).<br>- **Priority-routed schedulers.** `setTimeout` whose ms argument is dispatched between values based on a priority/option arg, OR whose dispatch routes to `requestAnimationFrame` for one branch and `setTimeout(fn, ms)` for others. NDS.debounce models a single constant ms; wrapping the dispatcher in `NDS.debounce(fn, ms)` collapses the priority branching. Motivating example: `overflow.schedule` in `_js/nds-main-nav.js` (~L240, with `'immediate'` → RAF, `'high'` → 10ms, `'low'` → 100ms).<br><br>If unsure, prefer a SKIP entry (with the specific orchestration shape named) over flagging the wrong pattern — JSP-07's value comes from being precise about what `NDS.debounce` actually replaces. | LOW | Use `NDS.debounce(fn, ms)` — store the wrapper once on the instance/closure and call it per event so the `clearTimeout` bookkeeping stays inside the helper. For single-pending-action latches and priority-routed schedulers, leave the inline pattern in place; consider extracting a richer scheduler primitive into core only if the same shape recurs in 3+ files. |
| JSP-08 | **MutationObserver without disconnect on lifecycle boundary.** A local `new MutationObserver(...)` bound to an element that nothing disconnects has an effectively unbounded lifetime despite its element binding. `check-js-rules.mjs` finds an observer assigned to a variable with no `.disconnect()` anywhere in the file (document-root observers and observers pushed to an instance array are skipped). It accepts a `.disconnect()` anywhere, so check it runs in the teardown path (`cleanup()` / `destroy()` / `reinit()` / `teardown()`), and that a component with no teardown path is not leaking per element. Complements JSP-05: JSP-05 covers pool-routing (is a local observer justified at all?); JSP-08 covers teardown hygiene (once local, is it cleaned up?).<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Observers whose JSP-05 exemption comment additionally states that the observer must outlive the element (rare; require explicit rationale, not just absence of disconnect). | MEDIUM | Store the observer handle on the instance (e.g., `this.observers.push(observer)`) and invoke `.disconnect()` in the teardown path. If the owning component lacks a teardown path but creates observers per element, either add the teardown path or re-evaluate whether the observer should be pool-routed via `NDS.onAttrChange` / `NDS.onDOMAdd` / `NDS.onDOMRemove`. |
| JSP-09 | **`onDOMAdd`-wired listener without `onDOMRemove` teardown.** A per-element listener attached inside an `NDS.onDOMAdd('selector', callback)` handler is never detached when the matched element is removed. A wiring guard (`if (el.hasAttribute(WIRED_ATTR)) return; el.setAttribute(WIRED_ATTR, '')`) prevents double-wiring but does NOT release the original closure, which stays rooted through anything it captured. `check-js-rules.mjs` finds an `onDOMAdd` callback body that calls `addEventListener` on a target other than `document` / `window` / `document.body`, with no `NDS.onDOMRemove` on the same selector in the file. Complements JSP-06: JSP-06 covers per-instance listener stacking; JSP-09 covers observer-wired listener stacking.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Listeners attached to a stable parent (event delegation) from inside the callback, where the parent's lifetime is process-long.<br>- `onDOMAdd` callbacks whose body invokes a module-level refresh / re-init routine (not per-element wiring inline), where the invoked routine is idempotent via its own guards — a `_ndsFooInitialized` / `data-nds-foo-initialized` marker on touched elements, an instance-level observer flag (`element._ndsFilterObserver = true`), or a whole-scope setup function that re-queries and rebinds as needed (e.g., `initFormControlClasses()`, `initInputAutoFill()`). These patterns delegate to a refresh-rather-than-per-element shape; the callback body does not itself carry the `addEventListener` the rule targets. See `setupManualFilter`'s `NDS.onDOMAdd` re-arm in `_js/nds-filter.js` (~L1694 — guarded by `element._ndsFilterObserver` / `n._ndsFilterBound`) and the `NDS.onDOMAdd('.nds-form-control', …initFormControlClasses)` pair in `_js/nds-form.js` (~L1754) for the pattern. NOTE: this exemption applies only when the invoked routine genuinely self-guards. If the routine re-attaches listeners unconditionally to the same elements on every invocation, the exemption does not apply and the finding stands. | LOW | Pair the `NDS.onDOMAdd('selector', ...)` subscription with an `NDS.onDOMRemove('selector', ...)` that removes or aborts the attached listener. If the element owns its own AbortController, abort it in the remove handler. If listeners are intrinsic to the element's content, prefer event delegation on a stable parent so no per-element wiring is needed. |
| JSP-10 | **Eager module-IIFE DOM work in loader-registered components.** DOM-walking work at the top of a loader-registered module's IIFE (outside any function or callback) runs inside the bundle's parse+execute task, before the loader's budget-slicer starts, so it can push that task past TBT's 50ms long-task threshold; `init()` is sliced, IIFE-top code is not. `check-js-rules.mjs` finds a `querySelectorAll` / `getElementsByClassName` / `getElementsByTagName` walk iterated with `.forEach` / `for` at the top level of the IIFE of a module whose namespace is in `_js/nds-loader.js`'s `COMPONENTS` array. It does not check the loop body, so confirm the body does DOM work: a `.style.*` write, `addEventListener`, `setAttribute`, a layout read, an observer or `NDS.on*` subscription, node insertion or removal, `innerHTML` / `outerHTML`, a class toggle, or a `hidden` / `data-state` / `data-status` toggle.<br><br>**Explicitly NOT a finding**:<br>- Annotation exemption (global) naming why the work must run at module load (e.g., `// FOUT-blocking — must run before next paint`). | MEDIUM | **Primary**: move the DOM-walking work into the component's public `init()` body — the loader's budget-slicer then manages it. Loader registration is already in place (detection requires it), so this is a cut+paste from IIFE top to `init()`. **Secondary** (work genuinely must run as the DOM parses, e.g., FOUT-blocking font swap, BFCache scroll-restore): wrap in `NDS.onIdle(() => { ... }, { timeout })` so it runs in an idle slot rather than extending bundle eval. **Tertiary** (one-shot bootstrap on a known-singleton root): defer the DOM walk separately via `NDS.onIdle(...)`. Rule is prophylactic — current HEAD has no findings, but future PRs adding IIFE-body DOM work bypass the budget-slicer. |
| JSP-11 | **Forced layout read on the synchronous `init()` / constructor path.** A layout read (`getBoundingClientRect()`, `offset*`, `client*`, `scroll*`, `getComputedStyle(...)`) on the synchronous path of a component's public `init()` or constructor, on an element already in the live DOM, forces a reflow inside the loader's critical init task and delays the `data-nds-loaded` reveal. The cold-init contract is that `init()` does cheap registration only (refs, listeners, observers) and defers all measurement until the element is shown. `check-js-rules.mjs` finds the reads directly in `init()` / the constructor and in a helper they call one level deep; reads inside nested callbacks are not listed.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Reads on an element the component just created and has NOT yet inserted into the live DOM (measuring a detached / off-screen build) — no full-page reflow forced.<br>- Reads already caught by JSA-02 (≥3 read/write alternations in the same function) — route there; JSP-11 does not double-flag.<br>- Annotation exemption (global) naming why the measurement MUST run at init before paint (e.g. FOUT-blocking, BFCache scroll-restore).<br><br>**Cross-reference:** JSP-10 keeps DOM *walks* out of the module IIFE; JSA-01 covers >50-element *loops* at init; JSP-11 covers the single forced *layout read* that no loop-count or alternation-count rule catches. | MEDIUM | Move the measurement into the element's first `NDS.onElementResize(el, handler)` callback (it fires an initial callback when observation starts — measure there), or build-while-hidden and measure on `show()` / `open()`, or push the math into CSS `calc()` so no JS read is needed. Reference: the cold-init refactors of `_js/nds-scroll-more.js`, `_js/nds-pagination.js`, `_js/nds-drawer.js`, `_js/nds-swiper.js` — each moved eager `init()` measurement into a ResizeObserver initial callback to kill the eager-init forced-reflow. If the read genuinely must run at init before first paint, annotate with a comment naming the constraint. |
| JSP-12 | **One-shot cancel handle re-armed without cancelling the prior one.** A cancel handle returned by `NDS.onTransitionEnd(el, fn)` and stored on an instance or element field (`this._cancelClose`, `panel._cancelAnim`) that is RE-ASSIGNED on a re-callable path (a `close()` / `open()` / swap method reachable a second time before the first transition settles) strands the prior handle with BOTH its `transitionend` listener and its fallback timer, so `fn` runs twice: state cleanup replays and any event the callback emits is double-dispatched. `check-js-rules.mjs` finds a stored handle assigned without the prior handle invoked first or an early-return guard at the top of the method. Complements JSP-04(b) — there the handle is never stored; here it IS stored, then overwritten.<br><br>**Explicitly NOT a finding** (do NOT flag):<br>- Annotation exemption (global) naming why the duplicate callback run is harmless. | MEDIUM | Invoke the prior handle on the line above the assignment — `this._cancelClose?.();` — or early-return on the state flag at the top of the method. Copy the pattern from `armTransition` in `_js/nds-panel.js` (~L91). |
