## R1 — Banner-first restore rule reads only the JS bundle, never cross-checks CSS

- **Source:** Report A
- **Area:** NDS IQ / banner-first release-picking rule, `NDS_ASSETS/js/nds-main.min.js` + `NDS_ASSETS/css/nds-main.min.css`
- **Mechanism:** The rule targets one bundle — the JS one at `NDS_ASSETS/js/nds-main.min.js` (and the mirror inside `NDS_ROOT/_site/assets/`). It never opens the CSS bundle. On Report A's install both bundles happened to lack a `Version:` line so the mismatch was moot for the decision, but the shape of the check leaves two failure modes silent: (a) one bundle carries a valid `Version:` line and the other does not — the check reads only the one it's told to; (b) both carry `Version:` lines but they disagree — the rule doesn't require them to match. Either shape is diagnostic of a hand-assembled runtime or an interrupted upgrade, which is exactly what the banner-first rule exists to catch.
- **Failure direction:** silent, and directional to false confidence — the agent proceeds on one bundle's answer while the other tells a different story.
- **Suggested fix (in the source's words):** *"Sanity-check the JS and CSS bundles against each other in the same runtime: same `Version:` (and same `Generated on:` when both are present). A mismatch is itself grounds to report and stop — either the runtime was hand-assembled from two builds, or a partial upgrade left one bundle stale."*
- **Scenario impact:** wants a behavior scenario where the fixture ships mismatched JS/CSS banners in `NDS_ASSETS` — correct action is to report the mismatch and stop, not proceed on the JS reading alone.

## R2 — "Dev deprecates the found runtime" is a valid path that reads as inferred

- **Source:** Report A
- **Area:** NDS IQ / banner-first rule, the no-`Version:` sub-cases
- **Mechanism:** The rule names three no-`Version:` sub-cases (`-dev` banner, plain missing line, banner matching no release) and one three-course dev decision (name the release, upgrade, rebuild). "Legacy, ignore" is not in the sub-case list and not in the three-course set. It works by chaining: dev drops the found runtime from consideration → the "No runtime anywhere in the project means first setup" rule then applies → latest release becomes the default. The chain is correct but derived. An agent operating conservatively could report "no course applies to your answer" and stall.
- **Attribution:** rules text — the chain is real, the derivation is a smell.
- **Suggested fix (in the source's words):** *"When the dev's answer to a reported non-conformant runtime is 'legacy, ignore,' proceed as first-setup: the latest release becomes the default, and the found runtime becomes a legacy artifact under the two-runtime exception in Workflow step 1's prior-NDS bullet."* One sentence, closes the derivation gap.
- **Scenario impact:** low — a comprehension scenario asking "dev says 'legacy, ignore' — what happens next" would guard the named case.

## R4 — Anchor's example path collides semantically with the wrapper name the reader is told to drop

- **Source:** Report A
- **Area:** `NDS-IQ.md` / anchor template (`NDS_ROOT = /path/to/nds-vanilla-template/`), §"The two paths"
- **Mechanism:** Two statements are consistent but the reader hits them in the wrong order. The anchor lands first, its example folder is *`nds-vanilla-template`* — the exact wrapper name §"The two paths" later tells the reader to drop. A first-time reader unzips inside `.nds/`, sees `.nds/nds-vanilla-template-v<version>/`, and reads the anchor as prescribing that folder as `NDS_ROOT`. Same shape as R10 from the 2026-08-12 triage (line-14 wrapper-as-NDS_ROOT ambiguity), but at a different attack surface: R10 was the "The two paths" prose leaning wrong; R4 is the *anchor placeholder* itself carrying the wrapper's own filename. Both fixes are cheap and orthogonal — landing R10 alone doesn't clear R4.

- **Scenario impact:** none — pure placeholder edit; the R10 first-install scenario (from 2026-08-12) already grades whether `NDS_ROOT/_site/` resolves directly, and would catch a regression here for free.

## R5 — CSP check absent from Workflow step 1's inventory; buried in the head-copy paragraph

- **Source:** Report A (biggest finding of the batch)
- **Area:** `NDS-IQ.md` §Workflow step 1 (project-wide decisions list), §"What to copy INTO this project" (Include-on-every-page bullet for the head), `_source/ui-shell/head.md` §CSP
- **Mechanism:** The rule exists — the Include-on-every-page bullet for the head warns: *"If the project sends a Content-Security-Policy, check it at install: the head carries one inline script that converts the deferred stylesheet preloads, and a `script-src` without an allowance for it blocks that script silently — grant it a nonce or hash, or half the styling never loads."* But it is embedded as an aside inside the head-copy paragraph — a place the reader hits when *copying* the head, not when *inventorying* the project. Workflow step 1's own list of project-wide decisions to raise at plan review (asset URL prefix, porting strategy, prior-NDS split, direction/locale, build pacing) does not include CSP. So a reader running the inventory is not cued to sweep for a CSP the project sends. Report A's session completed the whole inventory, wrote `NDS-PLAN.md`, worked the plan-review with the dev, and shipped the first ported page — without ever grep'ing for a `Content-Security-Policy` header, then hit the two blocked inline blocks (FCP gate `<style>`, theme-guard + deferred-stylesheet-loader `<script>`) on the first real browser hit.
- **Related wording:** Workflow step 1's *"The source answers before the dev does"* names CSP as *a constraint the source can answer* — but that's a rule about *answering* CSP questions once someone raises them, not about *proactively finding* a CSP in the host project. Both of Report A's reads skipped the aside; both were wrong under the rule, but the rule offered no failure mode at inventory time to catch it.
- **Suggested fix (in the source's words):** add CSP to Workflow step 1's decision list explicitly — *"Sweep the project's response middleware for a `Content-Security-Policy`; if one is present, name its `script-src` and `style-src` shape in the plan and adopt NDS's own CSP guidance from `ui-shell/head.md` (nonces when there is a server, hashes for a static host) before the first NDS page ships. The head unit's two inline blocks make this a first-render blocker, not a footnote."* Routes the fix through the source's own answer (which addresses R7's shape too), not through an ad-hoc workaround.
- **Scenario impact:** wants a behavior scenario where the fixture middleware ships a strict `Content-Security-Policy`; correct action names the CSP in the plan at inventory time and reaches for `head.md`'s CSP section before the first page. Converges with 2026-08-12's R9 and R12 — this is R12's *"the source is a first-class oracle, not a fallback"* pattern re-firing at a different rung.

## R6 — Pre-checklist smoke rung stops at "project-provided harness"; curl/headless are always available

- **Source:** Report A
- **Area:** `NDS-IQ.md` §Workflow step 4, the "Cannot see the page?" fallback paragraph
- **Mechanism:** The current fallback ranks channels as: project harness (puppeteer/playwright/e2e) → scripted run that captures console + `NDS.Init.audit()` → checklist for dev. Many projects don't ship the first, so the reader collapses to "no channel, emit checklist." Report A did exactly that, and the dev then hit a CSP failure that a 30-second `curl -sI` would have caught (the header is *on the response*) and a headless-chromium load would have made obvious immediately (console warning on first paint). Neither is documented, so both are invisible to a rule-abiding reader. The dev's checklist ends up being the second-cheapest option in practice, not the cheapest.
- **Suggested fix (in the source's words):** insert a smoke-test rung that needs no project setup, always available: *"Before delegating to the dev, run a smoke check that needs no project harness: (1) `curl -sI` the page — sanity-check status, `Content-Security-Policy`, `X-Frame-Options`, and anything else that would silently break a browser; (2) `curl -s` the page and read the returned HTML — head unit intact, page-scoped JS references resolve, no server-side render error leaked as HTML text. This is the pre-checklist minimum, and its outcome goes in the report. Only after a smoke check passes and no browser channel is available does the checklist go to the dev."* Makes the checklist a genuine last resort, not the first fallback.
- **Scenario impact:** wants a behavior scenario where the fixture page returns a strict `Content-Security-Policy` header that will block the inline blocks; correct action runs `curl -sI` before the checklist and names the CSP in the report, not after the dev hits it. Cross-refs R5 (proactive inventory) and R8 (inline-style grep).

## R7 — "Source answers before dev does" reads as a rule about *questions*, not about *fixes*

- **Source:** Report A
- **Area:** `NDS-IQ.md` Rule #3 (Copy canonical markup verbatim), Workflow step 1 ("The source answers before the dev does"), Include-on-every-page bullet ("Do not reduce the set or reorder it")
- **Mechanism:** After the dev reported the CSP violation from R5, the agent laid out three fixes (drop inline blocks / add hashes / server nonces) and *recommended dropping the inline blocks* — without reading `ui-shell/head.md`'s CSP section (which names nonces first, hashes second). The dev pointed at the source; reading it made the answer plain. The dev also caught that the agent's proposed drop was already reshaping the head unit — a structural edit the Include-on-every-page bullet expressly forbids ("Do not reduce the set or reorder it"). Two rules failed the reader together:
  - **Rule #3** governs *page markup*, not head-unit structure — its sanctioned-edits list (asset-URL rewrites, content swaps, modifier-class composition) is exhaustive by construction, but the ban on structural edits is inferred, not itemized.
  - **"The source answers before the dev does"** is written in terms of *questions* — the dev's or the agent's — not in terms of *fixes the agent would recommend*. So a reader hits the rule at question-time and passes it at fix-time.
  - Under a strict CSP the reader hits `head.md`'s Two Ways section and sees the plain-stylesheet path described alongside the gated one; that framing reads as a *menu the consumer can choose from*, not as a template-side design record already decided by the shipped head. So dropping the gated setup looks like consumer choice, not a structural rewrite.
- **Suggested fix (in the source's words):** two small changes.
  1. **Rule #3 sanctioned-edits list** — after the three kinds, add: *"Structural edits to a copied unit (drop or reorder members, change `rel`/`data-*` markers on head links, remove copied `<style>` or `<script>` blocks) are NEVER sanctioned as a workaround to a project constraint. If a constraint pushes back on the unit as shipped, the fix lives in the constraint or in NDS's own guidance on that constraint (e.g. CSP → `ui-shell/head.md`'s CSP section), not in reshaping the unit."*
  2. **"The source answers before the dev does"** — broaden from *questions* to *fixes*: *"Before you propose a fix that touches a rule or a component the source has direct guidance on (CSP, i18n, dark mode, RTL, initialization, focus management), read that guidance first. A fix picked from `.md` you did not open is home cooking; a fix picked from the source's own section is the sanctioned one, and the dev's review time goes to the trade-offs inside NDS's answer, not to catching you at the wrong answer."*
- **Scenario impact:** wants a comprehension scenario asking "the head unit's inline blocks are blocked by CSP — what do you do?"; correct answer reads `head.md`'s CSP section and reaches for nonce/hash, never proposes dropping the inline blocks. Cross-refs 2026-08-12's R12 (source-as-oracle) — this is the same pattern surfacing at *fix-recommendation* time rather than dev-facing-question time.

## R8 — Inline `style="--…"` in copied canonical markup is a rule-geometry trap under strict CSP

- **Source:** Report A (hit twice in one session, same root cause)
- **Area:** `NDS-IQ.md` Rule #3 (sanctioned-edits list) + Rule #5 (Component-knobs bullet's CSP branch), `_source/examples/sign-in.md`, `_source/templates/*.md`
- **Mechanism:** The sign-in canonical markup ships inline `style="--…"` knobs on individual elements (`style="--align: center"` on the outer stack, `style="--btn-padding: 0; --btn-width: 96px"` on the captcha's SVG holder) and on `<body>` (`style="--bg-img: url(…); --bg-opacity-top: 60%; --bg-opacity-bottom: 90%"` for the page background). Under a strict CSP with `style-src` locked down, a nonce can cover a `<style>` element but not a `style` attribute — so every knob dies silently on the port. Rule #5's Component-knobs bullet does name the CSP branch and the scoped-class escape path, but a reader following Rule #3 verbatim ships the inline attributes as-copied, and Rule #5's escape reads as an *audit-time* rule, not a *copy-time* one. Neither rule cross-references the other. Rule #3's Modifier-Classes exception sanctions *class composition* ("adding a class") but reads as an *additive* edit, not the *substitutive* edit CSP requires (*replacing* an inline `style` with a project-defined class). The reader hits Rule #3 during copy, ships the inline attribute, and never revisits Rule #5 until a browser complains.
- **Reach:** the same pattern surfaces at every layer where canon uses inline knobs — element-level (form knobs), page-level (`<body>` background), and by extension anywhere else shipped markup carries `style="--…"` stamps. Same class as R9 in the 2026-08-12 triage (strict-CSP conflict with canonical inline knobs), but reached from a different angle: 08-12's R9 was the head-doc CSP table being incomplete; this one is the *reader's rule-of-rules geometry* — Rule #3 and Rule #5 not intersecting where the reader lands.
- **Suggested fix (in the source's words):** two small changes.
  1. **Rule #3 sanctioned-edits list** — add a fourth explicit kind tied to Rule #5's CSP branch: *"(4) CSP-driven conversion: under a strict CSP that disallows inline styles, any `style='…'` attribute carrying a CSS custom property (`--*`) in the copied markup is replaced by a project-scoped class that sets the same custom property. The class rule ships in a nonce-covered `<style>` block. This is a *substitution*, not an addition — the shipped inline `style` is removed. It is the ONLY sanctioned substitutive edit; every other structural change to copied markup remains banned (R7)."*
  2. **Workflow step 4's smoke-test rung (R6)** — under strict CSP, the smoke curl should specifically `grep -oE 'style="[^"]*"'` the response HTML. Any survivor is a knob that will silently die in the browser, and the audit is one line of shell. Naming the check in the smoke rung is what a reader running the curl smoke test would remember before delegating to the dev.
- **Scenario impact:** wants a behavior scenario where the fixture ships a strict CSP and the ported page copies canonical sign-in markup verbatim; correct action substitutes each inline knob to a scoped class in a nonce-covered `<style>` block, and the smoke curl confirms no `style="…"` survivors in the response HTML.

## R9 — Host-stack idioms slip non-canonical structural additions past Rule #3

- **Source:** Report A
- **Area:** `NDS-IQ.md` Rule #3 (Copy canonical markup verbatim), sanctioned-edits list
- **Mechanism:** On the first port, the agent shipped a `<span asp-validation-for="X" class="nds-feedback nds-error nds-sm"></span>` after every `.nds-form-container` — a whole element the canonical form does not carry. Canon does field feedback through `data-error-message` on the input and a top-level `_ValidationSummary` alert for server errors. The span looked "styled with NDS classes" so it read as a small compatible add. It was not: it added structure canon does not ship AND it duplicated a mechanism canon already covers. The dev caught it immediately with the exact question — *"why break the rule to not match the canon?"* — the agent had not caught it during copy, nor during a structure-recheck pass the agent ran the same session.
- **Why the rule let it through:** Rule #3's sanctioned-edits list is exhaustive by construction, but the ban on "adding a new element" is inferred, not itemized. The trap is at a *different attack surface* from R7 and R8 (both CSP-motivated): this one is *host-stack-motivated* — the ASP.NET tag helpers, jQuery Validate spans, Rails `errors.full_messages_for`, Django `{% form.errors %}`, Vue/React validation slot components. Any framework you use has its own "per-field validation lives here" reflex. Under the port, the reflex quietly attaches non-canonical structure to canonical markup because the reflex adds *host-language content* (tag helpers, template partials) that renders as HTML the reader instinctively judges as *"just how framework X does forms."* The judgment skips Rule #3 because Rule #3 reads as an *NDS* rule and the addition reads as *framework* wiring — even when the addition is HTML that violates the copy.
- **Suggested fix (in the source's words):** extend Rule #3 with a named ban on host-stack-driven structural additions:
  > *"Never add host-framework structure to a copy. Any tag helper, template partial, or macro that expands into HTML the canonical source does not ship — MVC's `<span asp-validation-for>`, Rails' `errors.full_messages_for`, Django's per-field error blocks, Vue/React validation slot components — is a structural addition. The three sanctioned edit kinds do not include it. If the host framework normally wires that structure and NDS's canonical markup covers the same job through a different mechanism (`data-error-message`, `.nds-form-footer[data-feedback-target]`, `nds:formInvalid`, the top `_ValidationSummary` alert for server errors), the canonical mechanism wins and the framework wiring stays off the port. Host-framework helpers may still emit the *values* the input needs — `asp-for`, `v-model`, `f.text_field :name` — but never additional elements."*
- **Scenario impact:** wants a behavior scenario where the fixture is a Razor / Rails / Django form template; correct action ports the values through the host helper's *attribute-side* wiring only, and never emits framework-added validation elements alongside canon.

## R10 — "Template script blocks are canon too" is filed under Composition Cascade, not near Rule #3 or JS wiring

- **Source:** Report A
- **Area:** `NDS-IQ.md` §Composition Cascade (the script-block-canon paragraph), Rule #3 (sanctioned edits), §JS Wiring
- **Mechanism:** The rule is exact and correct — *"A template's or example's own script block is canon too. It encodes wiring the page needs — a stepper's last-step completion call, a form's reset loop — often with a comment saying why the line exists. To change its behavior, edit the copied script point by point against the original; never rewrite it from scratch from what you think the page needs. A rewrite silently drops pieces the original still needs."* It lives in the Composition Cascade section — the block a reader visits when *picking a template or example*, not when *writing the page's JS*. By the time the port reaches its JS phase the reader is in either Rule #3 (markup verbatim) or §JS Wiring (consuming NDS's own component APIs); neither restates the script-block canon discipline. On Report A's port, the agent wrote `login.js` from scratch (`DOMContentLoaded` handler designed around the port's perceived needs) instead of adapting the sign-in example's own `<script>` block point-by-point. Consequence: the submit loading state, the `pageshow` bfcache reset for loading buttons, and the `withLoading` pattern's shape all went missing. Dev caught it — *"no loading when submit like source, the inline js logic are part of canon in examples and full page DGA templates."*
- **Same class as R5, R7, R8 above:** the rule exists and is correct, but its section-of-record is not the section the reader is in when the trap opens.
- **Suggested fix (in the source's words):** move (or duplicate) the paragraph into the JS wiring section under a named rung, e.g. *"Adapt canon scripts point-by-point, never rewrite."* One extra sentence in Rule #3's sanctioned-edits list would also close the geometry: *"When copying a template or example, the page's own `<script>` block is part of the copy under the same rule. It may only be edited point-by-point against the original — the ban on structural additions (R7, R9) and the ban on substitutive rewriting (this rule) both apply."* Folds the script-block rule into the same one-stop location Rule #3 already occupies for markup.
- **Scenario impact:** wants a behavior scenario where the fixture ports the sign-in example and the correct answer copies the canon `<script>` block wholesale (edited point-by-point for selectors), never rewrites it from a DOMContentLoaded handler the agent designed. Cross-refs 2026-08-12's R12 (source-as-oracle) — same pattern at the JS-writing rung.

## R11 — Loading state persists across `[hidden]` card toggles; the canon comment names the mechanism, not the discipline

- **Source:** Report A (source-side fix landed 2026-08-13)
- **Area:** `_source/examples/sign-in.md` (canonical `<script>` block), `_source/examples/registration.md`
- **Mechanism:** The sign-in canon's `[hidden]` toggle paragraph comments: *"Plain [hidden] toggling: no NDS component swaps sibling cards (Panel is a slide-in surface, Stepper only stamps the indicator), so this stays native."* That says *why* it stays native, but not the consequence: **native toggling runs no lifecycle**, so any state that lives on children of a hidden card (loading, disabled, aria-expanded, validation feedback, populated form values) survives when the card comes back. Report A's port shipped a submit loading state; the dev clicked cancel on the credentials card, the card hid via `hidden`, the `[data-state~="loading"]` on the submit stayed set, and re-revealing the card by clicking its trigger again showed the spinner still running on a submit that had never actually gone anywhere. Dev caught it — *"when click cancel btn and go back should also remove loading."* The card-swap family is exactly what the sign-in canon itself demonstrates: start / credentials / delivery / otp / account / password / mobile / out — eight cards toggled by `[hidden]`. Any of them can carry a loading state that survives a cancel. Reader gets one comment naming the mechanism, none naming the discipline the mechanism requires.
- **Source-side fix (already landed):** the two source examples that use `withLoading` — `_source/examples/sign-in.md` and `_source/examples/registration.md` — now (a) drop `btn.disabled = true`, so the visual loading state is the only pattern; (b) guard re-entry on the `nds-loading` class; (c) stamp `aria-busy="true"` on entry and remove it on exit; (d) expose a `cancelLoading()` that clears the pending timer, drops the loading class, and removes `aria-busy`; (e) wire cancel / back / back-to-start handlers to call `cancelLoading()` before navigating. Ships as commit `ad4c7c86`. The example canon now *models the discipline in its own script block* — R10's "script blocks are canon" rule means a consumer copying the block gets the reset pattern for free.
- **Suggested fix (rules side, in the source's words):** add one line to the same paragraph the sign-in canon uses to explain `[hidden]` — *"Because `[hidden]` runs no lifecycle, resetting state — loading spinners, disabled attributes, validation feedback, populated form values — is the caller's job on every card-swap transition, not just on the first paint. A `cancelLoading()` (or equivalent reset) next to `show()` is the shortest pattern; the sign-in canon script models this."* Names the discipline in the same paragraph that names the mechanism, so the trap is visible at design time, not at bug-report time.
- **Scenario impact:** none, given today's source fix — R10's script-blocks-are-canon rule + the canon script now carrying the pattern together grade the discipline. If the rules-text sentence lands, a comprehension scenario asking "cancel is clicked mid-loading on a `[hidden]`-toggled card — what happens?" would guard it.

## Cross-cutting pattern: R7 + R8 + R9 + R10 all cluster around Rule #3's inferred bans

Four findings all describe the same failure at Rule #3's edit-boundary from different attack surfaces:

- **R7** is the *structural-edit* trap under CSP (drop head-unit inline blocks as a workaround).
- **R8** is the *substitutive-edit* trap under CSP (replace inline `style="--…"` with a scoped class).
- **R9** is the *host-stack-additive* trap (add `<span asp-validation-for>` because the framework's reflex says so).
- **R10** is the *script-block-rewrite* trap (write `login.js` from scratch instead of adapting the copied block).

Rule #3's sanctioned-edits list is exhaustive by construction — anything not on it is banned — but the reader doesn't experience it as exhaustive. Every one of the four bans is *inferred*, and every inference fails at a different reader-mental-model boundary. Fix candidates should land together as a single Rule #3 rewrite that itemizes the full ban set (structural, substitutive-under-CSP, host-stack-additive, script-block-rewrite) with named cross-references, rather than as four separate one-liners that leave the rule shape unchanged. The one *sanctioned* substitutive edit (R8's CSP-driven conversion) belongs in the same rewrite so the reader sees the boundary in one place.

## Cross-cutting pattern: R5 + R6 + R8's grep line all live in "install-time verification"

R5 (proactive CSP inventory at Workflow step 1), R6 (curl smoke rung before dev checklist), R8's smoke-grep for surviving `style="…"` attributes all describe the same missing rung: *the check that would have caught the failure before the browser did.* This is the 2026-08-12 pattern **"the rulebook documents the correct end state, leaves the steps ambiguous, and puts key detail in a secondary section"** re-firing at install-time rather than upgrade-time. Landing R5 + R6 + R8-smoke as a single "install verification" rewrite (Workflow step 1 gains CSP; step 4 gains the smoke rung; the smoke rung carries the grep line) is cheaper than three separate one-liners, and grades cleanly under one behavior scenario (fixture ships strict CSP; correct action names it at inventory, curls before checklist, greps for surviving inline styles).

## Cross-cutting pattern: R7 is R12 (2026-08-12) firing at fix-recommendation time

The 2026-08-12 triage's R12 — *"the source is a first-class oracle, not a fallback"* — was diagnosed at *dev-facing-question* time (agent opens a decision matrix instead of reading `_source/`). R7 is the same principle failing at *fix-recommendation* time (agent proposes a fix instead of reading the source's own answer). Both R5 and R10 above are additional firings — R5 at *project-inventory* time, R10 at *JS-writing* time. Together they suggest R12's discipline should be restated as a *phase-independent* rule rather than tied to any one workflow moment. Section names to check: `_source/ui-shell/*.md` for chrome/CSP/i18n/direction, `_source/examples/*.md` for chrome-shape and page-family archetypes, `_source/core/*.md` for initialization/focus/state, `_source/_data/content/*.yml` for component/example catalog matching."*
