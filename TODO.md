## Design threads — next NDS IQ cycle (parked 2026-08-11, needs careful planning; do not edit the rules piecemeal)

One connected rework, surfaced in the 2026-08-11 versioning discussion. **The principle underneath all three, and the line to open any plan with: the template has migrations, NDS IQ does not — so the template needs version gates and NDS IQ needs none.** A newer revision is just better instructions; it cannot break work already done in the dev's project, so the worst case of a missed update is "runs slightly older instructions", which is stagnant, not broken — and recoverable anyway, since the setup prompt is already an unconditional pull. Today the rules gate both the same way, with the same ceremony, when only ONE of them can break a user's project. The three items below are the same deletion on three surfaces: item 1 removes the floor gate, item 2 removes the version-conditional source layout, item 3 removes the update gate. Plan them together, not as separate sentence edits.

**The benefits compound, and the last one is the point:** one uniform process across every template version (no "1.7.0 and up does X, older does Y" branch) → a simpler release process (`mkrelease.py` stops assembling and verifying `_source/`) → **less instruction text** → less agent noise and better comprehension on the weakest tier the file serves → **fewer scenarios needed to guard it**. Every conditional branch removed from the rules is a distinct behavior the suite no longer has to pin, so this rework slows the suite's growth rate, it does not just pay a one-time cost.

- [ ] **1. The 1.7.0 floor is over-strict, and its stated premise is false.** `NDS-IQ.md:24` claims a banner below 1.7.0 has "no supported reference to install". Not true: GitHub auto-generates **Source code (zip)** for every tag (`archive/refs/tags/v<version>.zip`), retroactively, for every release already shipped. It carries `components/*.md`, `_sass/`, `_js/` at that exact version — so canon always exists and always matches the runtime. What a sub-floor release actually lacks is narrower: per-file JS banners and the `_source/` layout. That is DEGRADED, not blocked, and `components/*.md` (the rules' own "first stop for how to write a component") long predates 1.7.0. Draft replacement, roughly length-neutral: *"Below 1.7.0 the release zip has no `_source/` and its JS carries no banners. Install the matching tag's Source code zip (`archive/refs/tags/v<version>.zip`) — same version, so canon still matches the runtime — and read component canon from `components/*.md` instead of banners. Report what is degraded and propose the upgrade: the dev's call, not a block."* The one risk worth keeping is NOT "can't read docs" but **reading canon NEWER than the runtime** — so the fetch must be the MATCHING TAG, never raw main.
- [ ] **2. `_source/` may not need to ship in the template zip at all.** Fetch it separately into `NDS_ROOT` (`.nds/`) on demand — the same motion the restore bullet already describes for the template itself, so it is not a new concept. **One download, not per-read**: reads stay local afterwards, so nothing becomes network-dependent at use time. Likely needs no `mkrelease.py` work either — GitHub's auto Source code zip already exists per tag, so a hand-built source asset is probably redundant. Touchpoint, not a blocker: `verify()` currently fails the build if any path the rules reference is missing from the zip, *including the bare `_source/…` ones* — that guard changes shape, it does not just get deleted.
  - **Fetch mechanics, already pinned down.** The name comes from GitHub itself, derived as `<repo>-<tag>` with the tag's leading `v` stripped — tag `v1.7.0` gives `NDS-vanilla-1.7.0.zip`, holding one top folder, `NDS-vanilla-1.7.0/`. **Nothing in `mkrelease.py` produces or can rename it**, which is the upside (free, retroactive, no build work) and the constraint (the rules must accept the name as given, and it will never match the template zip's convention). **Its layout is the REPO root** (`components/`, `_sass/`, `_js/`, `_data/content/` at the top), NOT the template zip's `_source/` layout. So the lazy extraction is: put that folder's CONTENTS into `NDS_ROOT/_source/` — which leaves every `_source/…` path the rules already reference valid with **zero text changes**, and matches how the eval harness already maps them ("the zip's `_source/` is a straight copy of the repo's own folders"). Watch one detail: the source zip's wrapper folder is named `NDS-vanilla-<version>`, not the release name the template zip uses, so the existing "put that folder's CONTENTS at the declared path" instruction only covers both if it stays generic about the wrapper's name.
- [ ] **3. The revision number may become a USER-FACING indicator only (e.g. `0.8` to read as beta), with NO mechanical logic attached.** This is NOT the `v0.7` idea rejected below — that one kept the number load-bearing. This one decouples display from machine. **It is only safe once nothing compares the number, and today three things do:** step 4's replace gate (`NDS-IQ.md:231`), the read-only "are we current?" check (`:226`, where the comparison IS the answer, so this one may need to survive in some form), and `mkrelease.py:96,298,354` plus both guides' Liquid `split`. **And the constraint no edit can remove: every `v7` copy already installed in the field runs v7's gating text, not the new text** — so a `0.8` heading reads as older to them (plain arithmetic, not a parsing quirk) and they refuse the download that would fix it. Whether that matters is a judgment about the real install base, which is the dev's call and belongs in the plan, not in a rules edit. Cheap escape if it does matter: keep the machine counter in the file and put the human-facing `0.8` only on the guides' Beta chip.
- **Universality is non-negotiable across all three.** The file stays byte-identical in every install — zero per-project values, update = whole-file replace. So version-conditional behavior must be written as a rule the agent EVALUATES at read time ("read the runtime banner, fetch that tag"), never as a value baked into a copy, and never as a per-project variant of the file. The project's two paths live in the anchor and nowhere else; nothing in this rework may push a second per-project value into the rules file.
- **The bill is the suite, not the file — six scenarios, and the skill itself. But it is partly a REFUND, not a cost:** removing a conditional removes the behavior it guarded, so some of these are deletions and simplifications, not rewrites. Best current read: **S47 likely deletes outright** (with no gate, the only remaining risk is the corrupt download, which S42's install path already checks via the `# NDS IQ` first line — do not keep a scenario for a rule that no longer exists), **S18 gets repurposed rather than deleted** (the degraded path — fetch the matching tag, report what is degraded, proceed — is new behavior and still needs a guard, but a simpler one than the stop), and **S1, S25, S17, S4 take rubric edits**, since the floor is one clause among several in each. Confirm that split when planning; it is an estimate, not a verified count. Enumerated 2026-08-11 by matching every scenario's `rules:` line against the floor and compare sentences; grouped by which item breaks them. **Floor change (item 1):** **S18** `template-floor-stop` (its entire MUST is the stop), **S1** (baselined twice on "sub-floor runtime = upgrade is the PREREQUISITE", including a 2026-08-05 fix and re-probe for exactly that reading), **S25** `banner-first-wiring` (its `rules:` names "an `NDS_ROOT` below the floor takes the floor paragraph, banners or not" — and banners are precisely what a sub-floor reference lacks, so this one changes MEANING, not just wording), **S17** `banner-first-install` ("which release" to populate `NDS_ROOT` is the same decision the floor gates), **S4** `block-refresh-runtime-behind` (upgrade steps 1–4 plus "Runtime behind the latest release? Note the false positives excluded: S2, S19, S32, S33, S36 all cite a "step 4" — but that is the WORKFLOW's step 4 (verification), a different step from the Upgrading section's step 4 (update this file). Do not let that collision widen the bill. Scenario rewrites land BEFORE the sentences, per this file's standing rule, and the rework moves SKILL-side artifacts too — rubrics, baselines, and `last-evaluated.md`, not just the rules text.
