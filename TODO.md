- [ ] **Field findings 2026-08-18 — NDS 1.8.1 / NDS IQ v2.2.** Two feed the v3 rework above; four are NDS code/doc. Kind: **gap** = API hole; **papercut** = works as documented but silently traps a reasonable reader; **doc-trap** = behavior correct, banner misleads.
  - [ ] **papercut.** `_js/nds-cooldown-button.js` `data-cooldown-label` substitutes only `{s}`; `%s` renders literally with no warning. Why it matters: printf is the more universal reflex, and the miss is silent until the cooldown first fires in prod. Fix: accept both at the helper's substitute (`/\{s\}|%s/g`), and generalize to any single-token `data-*-label`.
  - [ ] **gap.** `NDS.CooldownButton.start(btn)` always dispatches `nds:cooldown:triggered` — no way to prime just the cooldown UI. Why it matters: any flow whose first action is outside the cooldown button (initial-send, restored state) either double-fires the request handler, ships a suppression flag, or reimplements the timer. Fix: `startCooldownOnly(btn)` or `start(btn, { fireEvents: false })`.
  - [ ] **gap.** `data-sent-title` / `data-sent-message` fire on `nds:cooldown:triggered` (click) — the toast is bound to a client-side clock event, not the request outcome. Why it matters: on request failure the built-in "sent" toast fires alongside the consumer's error toast, contradicting it. Fix: `data-sent-on="triggered|success"` (default `triggered`) + `NDS.CooldownButton.markSent(btn)` from `.then`. Stopgap: banner rewrite naming the trigger as click, not success.
  - [ ] **doc-trap.** `nds:cooldown:loading` never fires at default `data-cooldown-loading=0`; banner lists the event as first-class without naming the coupling. Why it matters: a consumer wiring the request to `loading` sees the countdown start with no network activity and no console signal. Fix: append " — only fires when `data-cooldown-loading > 0`" to the banner line, or default `loading` to `1`.
  - [ ] **gap.** §Plan tick-box rule in `_includes/NDS-IQ.md` is ambiguous on scope, preservation, and historical conversion — "open items are tick boxes… ticked when it resolves" reads two ways. Why it matters: two-style plans ship (new sections boxes, old sections prose), which is the drift the rule was written to prevent; deleted `[x]` history costs cross-session memory. Fix: widen "open items" → "plan progress", add "never delete a resolved item," name historical conversion.
  - [ ] **gap.** §P1 "check before claim" trigger fires only when the reader articulates a claim; a reader who just starts coding an obvious pattern skips it. Why it matters: mnemonic triggers decay through a long session (attention, compaction, momentum), so the reader most in need is the one who's missed the moment. Reinvention evidence in one session: `NDS.OTP.clear`, `NDS.Forms.clearStatus`, whole `NDS.Password` component. Fix: mechanical §Build step — "before you write page JS — catalog + banner check first." Distinct from §JS wiring's existing trigger, which covers hand-rolled utilities (fetch, debounce, listeners); this one covers hand-rolled component behaviors (password rules, OTP clear, tag input, autocomplete, date picker, sortable table, filter chips, live search).
