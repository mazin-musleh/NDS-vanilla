- [x] **INVESTIGATION — who owns ordering when the server owns the rows? CLOSED 2026-08-14, by design, no source change.** Sort is the one thing the AJAX request drops, and unlike the slider that is correct — it is not in `criteria`, so the filter never claimed it, and a dev who owns sorting names their own form control instead.

  **Measured** (`scripts/check-filter-server-mode.mjs`): after an apply, `?sort=name&dir=asc` sits in the browser URL while the request carries none of it — the request is exactly `FormData(submissionForm)`, asserted in that harness. `updateUrlParams` deliberately preserves `sort`/`dir` as NDS.Sort's (`_js/nds-filter.js:816`), and `_applyAjaxResponse` calls `_resyncSort()` so the sort engine re-roots onto each swapped-in container.

  **The concern, untested:** in server-driven mode the response holds ONE page of rows. A client-side sort then re-orders that page only, which looks correct on screen and is wrong across the result set — row 1 of page 2 may belong above everything on page 1. `_resyncSort()` says the current design intends client-side sorting to keep working after a swap, so this is a real design question, not an oversight.

  **The precedent that probably decides it:** `NDS.Filter.refresh` already skips form-mode instances because "the server owns their result set" (banner, `_js/nds-filter.js:14-15`). If the server owns the rows, it plausibly owns their order too — which would point at sending `sort`/`dir` with the request and standing the client-side engine down in AJAX form mode, not at leaving both half-active.

  **MEASURED 2026-08-14** (`scripts/check-filter-sort-ownership.mjs`, headless Chrome against the dev server). All three questions answered; the split is real and complete:
  - **The client re-orders the server's rows.** Server response carried `Mango,Apple,Zebra`; with `?sort=name` in the URL the DOM after the swap read `Apple,Mango,Zebra`. `_resyncSort()` re-creates NDS.Sort on the swapped-in container, and `init()` → `_readUrl()` → `apply()` reorders. So `_resyncSort` does not merely re-root — it re-applies.
  - **A sort click re-orders in place and fires NO request.** Clicking the desc trigger after a swap: 0 requests, DOM `Apple,Mango,Zebra` → `Zebra,Mango,Apple`, URL `?sort=name&dir=desc`.
  - **Sort never reaches the server.** Request query was EMPTY while the browser URL held `?sort=name`.
  - **Fixture lesson worth keeping:** the filter creates NDS.Sort with `mode: 'direct'`, so a trigger does NOT toggle — `_onTrigger` reads `data-sort-dir` off the trigger and defaults to `asc`. A single `data-sort="name"` button with no `data-sort-dir` re-applies asc forever and looks like a dead trigger. Any future sort fixture needs the asc/desc pair.

  **RESOLVED 2026-08-14 — by design, no source change. The UI API already delivers server-side sorting.** Q5 measured the setup a dev who owns sorting actually authors: a form-mode AJAX filter with NO `[data-sort]` triggers and the dev's own `<select name="sort">` in the form. Result: `clientSortEngineCreated: false` (`setupSort` returns early with no triggers, so nothing client-side claims the order), the request carried `sort=price_desc&category=news` — the dev's sort key and the filter's criteria together — and the server's row order came through untouched (`Mango,Apple,Zebra`, unsorted). One request, zero NDS changes. This is why server-side sorting has been used in the field with no limitation reported, and it is the ordinary NDS shape: the component supplies UI and hooks, the dev owns the request. `data-sort` IS the client-side engine — authoring it is opting IN to client sorting. The Q1–Q3 split therefore only appears when someone puts the client engine on server-paged rows, which is mixing two tools, not a component defect. **Both fix options below are WITHDRAWN** (the warning included: it would fire on a combination the dev chose). Reopen only on a field report from a dev who used the documented server-side shape and still lost ordering.

  **Side observation, unresolved and possibly a fixture artifact — do NOT act on it as written.** In both fixtures the filter wrote no criteria to the browser URL after an AJAX submit (`browserUrlAfter` empty even with `category` checked and a settle before submit), while `updateUrlParams` plainly sets `criteria.filters` keys (`_js/nds-filter.js:868`) and earlier work observed chips/badge/URL agreeing. Something in the harness fixture differs from a real page. Unrelated to sort — chase it only if a URL-sync question comes up on its own.

  **Superseded — the framing that was open before Q4/Q5 ran, kept so it is not re-derived.** Two shapes both ship today and the component cannot tell them apart from what it currently reads: (1) server filters and returns ALL matching rows, client pages via `data-auto-pagination` and sorts — the client sort is CORRECT and complete, and standing it down would be a real regression; (2) server pages (`data-page-url` nav) and returns one page — the client sort re-orders that page only, which looks right and is wrong across the result set. The filter only looks for `.nds-paged-content` (`updatePagination`, `_js/nds-filter.js:2751`), which is the client-side wrapper, so it has no server-paged signal today. **No field report of sort breakage exists** — server-side filtering has worked in the field — so this stays theoretical until one lands. Options costed: (a) warn when the wrong combination is detectable (AJAX form mode + a `[data-page-url]` nav + an active sort) — cheap, breaks nothing, catches only the bad case; (b) carry `sort`/`dir` into the request and stand the client engine down in AJAX form mode — bigger, needs a Migration entry, and regresses shape (1).
